# AlphaAvatar v0.6.8 Release Notes

> Draft — work in progress on `refactor/rtc-provider-decoupling`. These notes describe the implemented foundation and remaining scope; they do not announce a published v0.6.8 release. Media adapters now live in `avatar-rtc`, application assembly and RTC lifecycle coordination live in `avatar-host`, and external messaging bridges have been removed. Full LiveKit Agents removal, shared Provider service and native streaming integration, Host CLI expansion, logging, and installation/configuration redesign remain pending.

## Highlights

AlphaAvatar v0.6.8 focuses on processor-owned capabilities, explicit runtime ownership, configuration-driven inference, and a clearer plugin workspace.

- Persona and Memory capabilities are organized into independently managed processors.
- Runtime capabilities and committed-turn streams replace metadata-only and ad hoc turn integration.
- Shared voice components are owned by one Foundation runtime and borrowed by consuming plugins.
- Inference startup selects runners from the active configuration; selected runners resolve model files during initialization.
- Plugin packages are grouped into Foundation, Perception, and Tools without changing public Python namespaces.

## Processor-owned Persona and Memory

Persona's Profiler, Speaker, and Face capabilities own their processor configuration and lifecycle. Profile extraction keeps its prompt, output schema, and business provider next to the Profiler processor.

Memory follows the same processor-owned organization. Its storage refactor separates durable memory records from session-specific file organization, while shared workspace paths provide consistent resource locations.

Concrete Persona and Memory behavior remains in plugin implementations. Agent-side contracts do not absorb their business logic.

## Committed turns and runtime capabilities

Committed-turn publication provides a dedicated turn-level stream for downstream consumers. Memory and Persona consume committed turn data rather than reconstructing turn boundaries independently from raw events.

Runtime capabilities provide concrete definitions and callable bindings where appropriate. The distinction between a descriptive capability and an invokable operation remains explicit.

## Router organization

Addressing and turn-taking implementations now live with their processors. Processor-owned configuration replaces the large centralized configuration definition.

The Router factory passes each processor its corresponding configuration subtree and respects processor enablement. Turn-taking coordination retains current addressing evidence through timeout resolution, waits for required transcripts before committing, and tracks assessment workers through cancellation and reset.

These runtime changes precede the physical plugin-layer migration; the directory move itself does not alter routing or decision policy.

## Module plugins and runtime lifecycle

`AvatarModulePlugin` owns module-factory registration independently of LiveKit's plugin registry. `AvatarRuntimePlugin` remains the session lifecycle contract.

Runtime package exports are loaded on access. Type-only configuration imports do not force the runtime package to load the full configuration composition during interface imports.

## Foundation runtime

`AvatarRuntime.foundation` contains a single `FoundationRuntime`. Its current `VoiceService` owns reusable VAD, STT, and TTS components.

Router receives `runtime` directly and obtains its base components through the foundation. The former `InteractionRouterDependencies` wrapper is removed.

Application assembly owns the injected runtime. Consumers stop their tasks and streams before shared services are closed; the foundation does not duplicate per-stream state.

This does not introduce separate `VoiceRuntime` or `ProviderRuntime` objects. Provider has not yet been migrated into a foundation plugin; that work remains part of the later Provider and LiveKit removal scope.

## Configuration-driven inference

`prepare_inference_runners()` receives the validated `AvatarConfig` object. Plugin-owned selectors return the required runner classes without serializing the full configuration.

A compact startup plan stores method names and importable module/class identifiers for worker reconstruction. `InferenceRuntime` receives an explicit mapping instead of falling back to a global runner catalog. `InferenceRunner` retains only its execution contract.

Disabled Persona model processors do not select their corresponding model runners. Router model selection follows its processor configuration and STT availability. Foundation VAD selection follows the configured voice plugin rather than a single consumer's enablement.

Selection occurs before serving realtime requests. It is a startup snapshot, not a hot-reconfiguration protocol. Restart the CLI after changing enabled components.

## Model files and cache

Persona model specifications and resolvers live inside the Speaker and Face processor packages. Router and Voice use shared file-resolution utilities for cache lookup, integrity checks, locking, and temporary-file cleanup.

Selected runners resolve and load models during initialization. No separate `alphaavatar download-files` step is required.

The model cache is controlled by `ALPHAAVATAR_MODEL_CACHE`. `ALPHAAVATAR_MODEL_OFFLINE=1` and `HF_HUB_OFFLINE=1` require local model files; they do not disable remote LLM, STT, embedding, or tool requests.

Pinned checksums are enforced where provided. Sources without a supplied digest use the documented first-use local hash checks; these are not a publisher signature. User-specified model overrides remain distinct from default model integrity pins.

See [Model Loading](../model-loading.md) for the precise resolver behavior and cache layout.

## Three-layer plugin workspace

```text
avatar-plugins/
├── foundation/
│   └── avatar-plugins-voice/
├── perception/
│   ├── avatar-plugins-character/
│   ├── avatar-plugins-memory/
│   ├── avatar-plugins-persona/
│   ├── avatar-plugins-router/
│   └── avatar-plugins-status/
└── tools/
    ├── avatar-plugins-deepresearch/
    ├── avatar-plugins-mcp/
    └── avatar-plugins-rag/
```

The root workspace globs, release package paths, lockfile editable paths, and current documentation links follow this layout. Layer directories are not installable packages.

Airi remains a submodule of the Character package at its existing gitlink revision. Its checkout path changes with the parent package; its stable submodule name is retained.

Provider and independently pluggable Context services are future Foundation packages. Reflection is a future Perception package. The migration does not create placeholder distributions for them.

See [Plugin Layout and Boundaries](../../avatar-plugins/README.md).

## Native-client scope and application hosting

Application assembly and RTC lifecycle coordination live in `avatar-host`.
AvatarEngine manages its own processor lifecycle rather than owning RTC adapters.
CLI functionality remains part of Host; no separate CLI distribution is introduced.

Audio/video codecs, media inputs, and audio/status/transcript outputs live in
`avatar-rtc`. Input adapters receive PerceptionRuntime directly, while output
adapters receive OutputRuntime.

The external messaging bridge package, channel registry, message envelopes,
SDK text dispatcher, bridge handshake, and channel launch examples are removed.
Native text chat and the existing `chat`, `agent`, `audio`, and `video` session
modes remain supported.

New session IDs are generated independently of channel names. Client-supplied
session IDs remain unchanged.

Execution is still session-scoped. This change does not implement
connection-independent Episodes, persistent Context recovery, or Dream scheduling.

## Migration notes

Python imports remain under `alphaavatar.plugins.<plugin>`. Distribution names and entry points are unchanged by the layer migration.

Existing `voice`, `router`, `persona`, and `memory` YAML sections are not renamed to layer names. The physical move does not change model revisions, vector dimensions, inference method names, or model cache namespaces.

Update repository-relative paths in local launchers, IDE configuration, deployment mounts, and any `AIRI_REPO_DIR` override that points inside the checkout. Synchronize editable installs after applying the move:

```bash
uv lock --check
uv sync --all-packages --locked
```

Code integrating with the former `AvatarPlugin`, `InteractionRouterDependencies`, or the global `InferenceRunner` registry must use the current contracts. No compatibility aliases are introduced.

## Provider contracts and backend implementations

Public Provider contracts now live in `alphaavatar.agents.avatar.provider`.
SDK-specific model construction, input adaptation, structured parsing, and usage
normalization live in `alphaavatar.plugins.provider.langchain`.

Task configuration distinguishes the backend implementation from the model
provider. Installed backends are discovered through entry-point metadata and
registered through the existing AvatarModulePlugin mechanism.

Memory and Persona retain their business prompts and output schemas. Their
prompts use AlphaAvatar ModelPrompt and ModelInputSlot rather than LangChain
prompt objects.

Tool results now contain typed parts, including media. Text projection does not
replace the complete result. Unsupported adapters reject content they cannot
represent instead of silently discarding it.

Streaming contracts are defined, but the current LangChain task backend does not
advertise streaming execution. Shared Foundation Provider ownership, managed
client and trace cleanup, native streaming implementation, and the remaining
LiveKit Agents execution path are still being migrated.

## Remaining v0.6.8 scope

The following items are not implemented by this change:

- Removing the remaining LiveKit Agents dependency, including SDK-owned text ingress, model execution, final Assistant delivery, and worker/session integration.
- Integrating the shared Provider service into FoundationRuntime and connecting native streaming model/tool execution.
- Expanding the CLI inside `avatar-host` and improving logging.
- Simplifying installation and composing plugin profiles through bundles, with UI, TUI, agent-assisted, and manual configuration workflows.

Package versions and release tags are not advanced by this directory migration. Final release validation and publication remain separate steps.
