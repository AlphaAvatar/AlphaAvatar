# AlphaAvatar v0.6.9 发布说明

### 亮点

AlphaAvatar v0.6.9 让 v0.6.8 的原生运行时变得**可安装、可配置、可诊断**。Linux x86_64 安装包现在自带 Python 和 `alphaavatar` 命令；交互式 Setup 选择 Avatar 运行所需的内容，并只安装这些内容；`upgrade` 向前升级到与当前构建并列存放的较新构建，`cleanup` 删除不再使用的内容。配置保存在命名的 **bundle** 中，bundle 由带注释的 **profile** 组成，均由完整模板生成；凭据按名称保存在配置文件之外。

**`alphaavatar doctor`** 在不连接任何服务的情况下检查配置；经同意后，使用配置的模型和服务，在固定的语音和图像样本上运行一次简短会话。它报告丢失的句子在哪一环节丢失、各阶段延迟，以及每个 runner 的队列和执行数据。

实时链路在各个边界上变得更可预测。每个语音片段都以一个明确的转写状态结束；迟到的 final 在硬期限之前仍会并入其 Turn，超过期限后 Turn 带通知继续，而不是丢失输入。轮次判断跨越一句话内部的停顿累积语音，不确定时明确 HOLD，并在有上限的等待内解决不确定性。

参与者、身份和数据归属由同一个运行时组件负责：**ParticipantRuntime** 在需要时给出一个 Turn 属于哪些参与者。Persona 在一个会话中关联多个声音和人脸，并使用新的说话人向量模型。Memory 为混合批次保留已验证的 owner，按类型和 owner 读取记忆，并拒绝在同一存储中混用两个 embedding 模型的向量。

推理 runner 接收显式的启动输入，语音活动和轮次判断 runner 可以运行**多个 worker 进程**。每个 runner 都报告其队列和执行指标。

### 新增内容

#### 语音转写状态、迟到结果与关联

* 每个语音片段以且仅以一个转写终态结束：final 文本、空 final、错误、被拒绝、未收到 final 即关闭、已取消或已过期。日志记录的内容就是下游消费者收到的内容。
* 已确定的 Turn 的转写等待现在有一个观察点（`transcript_wait_sec`）和单独的硬期限（`transcript_timeout_sec`，默认 3 s）。在期限之前到达的 final 并入其 Turn。到达期限时，Turn 带 `voice.transcription_unavailable` 通知提交，之后到达的 final 被作废，不会附加到后来的 Turn。
* 观察点只报告仍在等待的转写。其 schema 默认值为 0.75 s；`demo.yaml` 以及 `config init` 和 Setup 写入的 profile 把它设为 3.0 s，与期限相同，因此它们在期限之前不会报告等待中的转写。
* 在语音活动积压缺口内开始的语音被报告为丢失并取消，绝不会以截断形式发布；只有在确认边界之后才接受新的语音。
* 在回答的语音正在合成时取消回答，会被报告为打断，而不是合成失败；在最终发布期间关闭会正常收尾，不产生错误。
* 片段转写按任意行结束符读取服务的流式事件，在一个流的各片段之间复用连接，并在事件循环之外加载其 SDK。
* 有界的输入追踪把每个片段与其转写请求、终态、final、轮次决定和已提交 Turn 的 cutoff 关联起来。它保存哈希后的标识，不含原始文本，并受数量、大小和存续时间限制。

#### 整句范围内的轮次判断与寻址

* 轮次判断维持一个开放的、按时间排序的输入窗口。一句话内部的停顿、匿名片段和说话人标签不再把它拆成多个独立的输入。
* 语音说完后，输入被封闭并等待其转写，同时下一份输入已经开始收集。两个阶段都有上限（`max_pending_inputs`、`max_window_segments`）。
* HOLD 决定会写明原因：语音未说完、是否说完不确定、寻址不确定，或正在等待转写。
* 不确定性在有上限的等待内解决（`speech_completion_wait_sec`、`addressing_wait_sec`）。在这类期限到达时提交的输入会附带通知，说明其是否说完或寻址对象不确定。
* 只有 Turn 实际提交后才推进进度；在提交期限（`commit_timeout_sec`）之后到达的提议会被拒绝。
* 语义寻址读取自上一个已提交 Turn 以来的对话，其等待从所需的转写可用时开始。
* Turn 通知会进入模型的上下文：无法转写的语音作为不可用语音保留在历史中，并告知模型只遵循最新一条用户消息中的指令。

#### 参与者、身份与 Persona

* **ParticipantRuntime** 负责把语音片段和人脸关联到会话参与者，并在需要时根据 Turn 自身的输入给出其参与者，而不是在准入时固定下来。已确定的关联在整个会话中保留，因此之后运行的读取方（例如会话结束时的 Memory）也能看到它。
* 一个声音或一张人脸在整个会话中是一个实体，跨越设备和来源世代。
* 一帧中有多张人脸时，按由近到远的顺序处理；在主参与者的设备上，最近的新人脸属于主参与者。
* 说话人向量模型现为 **CAM++ (zh-en)**，导出为 ONNX（约 28 MiB），在其 runner 首次初始化时下载。
* 短于一秒的语音不单独匹配：其音频会延续到同一来源的下一个片段。
* 已存储的声纹和人脸向量通过与每个会话的向量加权合并来更新，而不是被替换。
* 身份匹配阈值属于 Persona 设置：`speaker.identity_match_threshold`（0.6，CAM++ 向量的余弦值）和 `face.identity_match_threshold`（0.40）。

#### Memory 归属、恢复、检索与 embedding 空间

* 包含未归属语音的记忆批次，保留其已验证用户作为 owner。
* 检索按记忆的类型和 owner 读取，从不按 scope：Avatar 记忆所有参与者都可读，而对话、工具和环境记忆只有其用户 owner 可读，在任何上下文中都是如此。
* 失败的环境记忆批次只重试其自身范围：它不会吸收更新的输入，不会越过缺口提交，重放已存储的工作也不会让较新的检查点回退。
* 被动检索受 `retrieval.passive_timeout_sec`（3 s）限制，没有需要检索的内容时跳过 embedding 请求。
* **embedding 空间保护：** 每个文本向量存储记录生成它的 embedding 模型。Host 打开存储时，另一个模型或另一种维度的向量会在存储中任何内容改变之前被拒绝。多个 Host 同时打开一个新存储时，最终确定为同一份记录。
* Setup 只能提前检查已有本地 LanceDB 记录所能说明的内容：如果 bundle 为这样的存储指定了另一个模型，会在安装任何东西之前被拒绝。Qdrant 存储、实际向量维度以及记录无法说明的内容，都在打开存储时检查。在开始保留记录之前创建的存储，只按其自身的向量维度接受，并记录为推定。

#### 推理 runner、并行与指标

* 每个 runner 收到显式的启动记录（工作区、模型目录及其配置），而不是从进程环境中读取存储或工具设置。
* `runtime.inference.methods.<method>.workers`（1 到 8，默认 1）为声明自己可复制的 runner 运行多个独立的 worker 进程，每个进程有自己的模型副本。本版本中这类 runner 是 Silero VAD 和 Smart Turn v3；为其他任何 runner 设置 worker 数量，会在加载配置时被拒绝。
* 请求在每个方法各自的有界先进先出队列中等待，队列、执行和客户端各有独立期限。worker 被终止或超时后，请求绝不会被重放。
* 失败的 worker 会被重建，同时该方法的其他 worker 继续服务。每个方法的重启次数有上限（`restart_window_seconds` 内最多 `restart_limit` 次）；上限用尽后，Host 带错误停止，而不是无休止地重启。
* Host 健康报告中的按方法指标：worker 数、就绪 worker 数、执行中和等待中的请求、拒绝数、队列超时和执行超时，以及重启次数。

#### 配置、凭据与交互式 Setup

* 配置按 **bundle**（一个列出其 profile 的文件）和 **profile**（每个部分一个文件）组织，位于应用主目录下，应用设置中记录默认 bundle。
* `alphaavatar config init <bundle> --avatar-id <id>` 根据以参考 `demo.yaml` 为基础的模板，写出一整套完整、带注释的 profile；它从不覆盖已有文件。
* `alphaavatar config check [--json]` 按 `start` 的方式加载配置，但不连接任何服务。它指出出错的设置、没有值的变量，以及未安装插件对应的 setup 命令。
* `alphaavatar setup` 依次询问能力、每个运行部分的 Provider 和模型、所需的凭据，并在安装前显示分组摘要。它写出 bundle 时保留模板的全部注释。
* `alphaavatar setup <bundle>` 安装已有 bundle 的设置所需的内容，不再询问能力、模型或凭据。在终端上它仍会显示摘要并询问 `Install and enable?`；没有终端时无人值守运行。`--plan` 以 JSON 输出计划。已有的 bundle、profile 和已存储的凭据从不被覆盖。
* 凭据依次从环境变量、`ENV_FILE` 指定的 `.env` 文件、已存储的凭据文件（权限 0600）读取。空值视为未设置；日志和报告只写凭据变量的名称，从不写其值。
* 自有服务器的密钥保存在按其 URL 命名的变量中，只有该服务器能读取这个变量。

#### 独立 CLI、Linux 安装包、升级与清理

* Linux x86_64 基础包（glibc 2.28 或更新）自带 CPython 3.13 和 `alphaavatar` 命令。随后 Setup 把 bundle 所需的包安装到单独的环境中并加以校验；模型权重在其 runner 首次初始化时下载到模型缓存。
* `install.sh` 默认安装最新版本，也可以安装指定的 `--version`、`--file` 或 `--url`，并校验每个下载的 SHA-256。
* 安装器在用户 shell 启动文件中一个带标记的块里，把命令所在目录加入新终端的 `PATH`；它输出的 `Next` 行说明如何让运行安装器的终端找到该命令。在终端上首次安装之后，它会提议运行 Setup；Setup 失败或被取消时，已完成的安装保持不动。
* `alphaavatar upgrade [--check | --version | --file]` 在当前构建旁准备并校验目标构建，然后一步切换过去。切换之前任何环节失败，当前安装都保持不变。
* **`upgrade` 只能向前升级。本版本不提供回滚或降级。**
* `alphaavatar cleanup [--dry-run]` 只删除由安装器创建、当前安装已不再使用的构建和环境；从不触碰应用数据。

#### Doctor 与 CLI 显示

* `alphaavatar doctor [bundle] [--rounds N] [--no-metrics] [--json] [--list]` 先运行静态检查，静态检查不创建、不下载、也不连接任何东西。
* 在终端上经同意，或在没有终端时设置 `host.doctor.external_services: true`，它会像 `start` 一样启动运行时，但使用临时工作区，且不使用 RTC。然后运行一个固定场景（语音，或语音加视觉），共若干轮。
* 每一轮都按严格的预期答案检查。丢失的句子会归因到语音活动检测、转写、轮次判断或未知。
* 报告展示从语音结束到第一个音频帧的各阶段、转写耗时分解，以及每个 runner 的 worker、最长队列等待和最长执行时间。第一轮单独报告；之后的轮次以中位数和范围汇总。
* 诊断会话的数据及其本地向量存储放在临时工作区中，结束后删除。首次运行时下载的模型保留在配置的模型缓存中。远程向量存储可能保存真实数据，因此只有当配置把其远程存储标记为测试存储时，诊断才会使用远程存储；诊断写入其中的内容不会随临时工作区一起删除。
* 文本和 JSON 报告与 `config check` 经过同一个输出边界：在打印或导出任何内容之前，来自配置和环境的凭据会被替换，控制字符会被删除。
* 所有命令共用一种报告版式。在终端上，分组标题和值得注意的状态会着色；宽度随终端变化，过长的值在其所在列下换行。`NO_COLOR`、`TERM=dumb`、管道和文件得到相同的文本，只是不带格式。

### 安装

**Linux 安装包（推荐）：** 在 glibc 2.28 或更新的 Linux x86_64 上，

```bash
curl -fsSL https://github.com/AlphaAvatar/AlphaAvatar/releases/latest/download/install.sh | bash
```

安装器会询问是否立即运行 `alphaavatar setup`。新终端的 `PATH` 中已有该命令；在运行安装器的终端中，按其 `Next` 行操作，或者打开新终端，然后：

```bash
alphaavatar doctor
alphaavatar start
```

只有在安装器中的 Setup 被跳过或没有完成时，才需要自己运行 `alphaavatar setup`。

v0.6.9 是首个发布安装器所读取的 Linux 安装包文件的版本。指定版本、已下载的安装包或离线镜像，分别用 `install.sh --version`、`--file` 或 `--url` 安装；见 [DEPLOY.md](../DEPLOY.md) 和 [CLI 指南](../cli/README.md)。

**从源码：** 用于开发时，克隆仓库并使用已提交的 lockfile（`uv sync --all-packages --locked`）；要获取某个版本的源码，检出其 tag。源码检出通过 git 更新，而不是通过 `alphaavatar upgrade`。

**PyPI：** 将各个包发布到 PyPI 是单独的手动工作流。GitHub Release 并不意味着全部 16 个工作区包或与之匹配的版本都已在 PyPI 上。

### 从 v0.6.8 升级

v0.6.8 没有发布 Linux 安装包，因此 v0.6.8 的源码检出要升级到 v0.6.9，可以从源码升级，或者安装 v0.6.9 安装包并设置一个 bundle。内部契约和部分设置已更改，没有提供兼容别名：

* **`avatar.id` 为必填项。** 工作区是 `avatar.workspace_root`（完整目录），或应用主目录（`ALPHAAVATAR_HOME` 或 `application.home`）下的默认位置。模型缓存是 `application.cache_root`。`avatar.work_dir`、`AVATAR_WORK_DIR` 和 `ALPHAAVATAR_MODEL_CACHE` 会被拒绝，提示信息中会给出替代项。
* 健康服务默认绑定 `127.0.0.1`（之前为 `0.0.0.0`）。
* `voice.vad.min_silence_duration` 默认为 0.3 s（之前为 0.55 s）。语音大约提前四分之一秒结束；停顿较长的语音会分成更多片段送去转写，因此可能需要更多转写请求。
* 轮次判断设置已更改，未知名称会被拒绝：
  * `max_hold_sec` 现为 `speech_completion_wait_sec`；
  * `policy.commit_threshold` 被 `model.incomplete_threshold` 和 `model.complete_threshold` 取代；
  * `transcript_timeout_sec` 和 `commit_timeout_sec` 为新增设置。
* `runtime.engine.max_turn_candidates` 现为 `max_turn_inputs`。
* Persona 的说话人向量来自新模型，存储在新的 collection 中。v0.6.8 存储的声纹不再被检索，声音需要重新学习。
* Memory 可见性遵循上文的类型与 owner 规则；已有记录不做迁移。唯一 owner 是 Avatar 的对话或工具记忆不再返回给任何人。
* 配置的 embedding 模型与文本向量存储所记录的模型不同时，该存储会被拒绝。要建立单独的索引，请为存储另起名称；或者配置创建该存储时使用的模型。不会自动删除或重建任何内容。

### 验证

本版本的证据来自四类检查，分别报告：

* **离线测试。** 离线测试集（约 1,200 个测试）在每次 push 和 pull request 时于 Quality 工作流中运行，同时进行 lock、工作区、lint、格式、构建和安装检查。涉及数据归属、生命周期、身份和存储契约的改动还经过变异检查：依次移除每一项保护，确认缺少它时会有测试失败。
* **合成压力测试与长时间运行测试。** 这些测试在一台共享开发机上使用不加载模型的替身 runner。它们度量调度、排队、取消和恢复，其吞吐数据不代表模型、Provider 或设备的性能。
  * 30 分钟的并发长时间运行测试（4 个会话 × 3 个方法）中，每个请求都恰好完成一次，没有丢失或重复。
  * 反复终止 worker、反复启动和停止运行时之后均能恢复，所有子进程、描述符和 socket 都被回收。
  * 在固定 5 ms 的替身执行和持续积压下，两个 worker 的吞吐量约为一个 worker 的两倍。
* **使用真实服务的 Doctor 运行。** 这些运行在一台开发机上使用配置的模型和服务，采用 Doctor 的固定样本，每份报告 5 轮。
  * 被停顿分成两到三个片段的话语作为一个输入提交：在四个样本和两种静音设置下，40 轮中有 40 轮恰好提交了一个 Turn，没有提前回复，也没有丢失片段。部分轮次中缺失的句子，在转写服务返回的文本中就已缺失（见已知限制）。
  * 使用默认配置时，语音加视觉场景 5 轮全部通过。纯语音场景 5 轮均未通过：其中四轮在转写服务的文本中丢失了第二句；另一轮的 final 在 3 s 期限之后才到达，因此 Turn 按设计带通知提交。
  * 有两个阶段在每一轮都变短了（后 4 轮的中位数）：从语音结束到语音活动关闭缩短 240 到 260 ms，来自新的静音默认值；以及仅在没有可召回的合格记忆时，从已提交 Turn 到其上下文准备完成缩短约 240 ms。final 与其提交之间因寻址不确定而产生的约 0.5 s 等待没有变化。
  * 端到端的首音频时间还包含各次运行之间转写、模型和语音合成的波动，因此**不声称有端到端延迟改进**，也不把各阶段中位数相加为一个数值。
* **人工验收。** 维护者验收了真实通话、安装包安装和 Setup。

Linux 安装包工作流在 `manylinux_2_28` 中构建安装包，并在没有 Python、Node 或编译器的干净 Ubuntu 24.04 容器中安装。候选版本还在一个使用虚构凭据的干净 Ubuntu 24.04 根文件系统中检查过：安装器进入了参考 bundle 的真实 Setup（105 个包，约 514 MB，所有 runner 均通过校验），从较早 CI 构建的升级以及一次清理都已完成，应用数据保持不变。

### 已知限制

* 仅支持 Linux x86_64。安装包按需要 glibc 2.28 构建，但安装只在 Ubuntu 24.04（glibc 2.39）上实际运行过。语义寻址需要 x86-64-v3 CPU。安装器不支持 Windows、macOS 或移动设备。
* 没有回滚或降级。`cleanup` 不检测正在运行的 Host：请先停止所有 `alphaavatar start`、`dev` 和 `doctor`。
* Setup 不安装 RAG 或 Character。`config check` 和 Doctor 都不连接 RTC 服务器：LiveKit 凭据要到 `start` 或 `dev` 连接时才首次使用。
* 在 Doctor 的固定两句样本上，默认的片段转写模型（`gpt-4o-transcribe`）经常只返回第一句（20 次运行中有 7 次返回了两句），Doctor 将这样的轮次报告为失败。丢失发生在服务返回的文本中。其他受支持的模型能完整转写该样本，但在多语言和混合语言语音上表现更差，因此保留该默认值。
* 对于未经语音活动检测就发送的静音或噪声，转写服务可能编造文本；经过正常的语音活动链路时，静音和噪声样本没有形成语音片段。
* 不可用语音通知依赖模型只遵循最新一条用户消息；这只用一个模型（`gpt-5.6-luna`）检查过，应换用另一个模型再次检查。
* Persona 说话人和人脸匹配只在公开的中文和英文录音上做过离线评估。多人会话中的身份识别仍在进行中：相似的声音可能被绑定到同一用户，一个人的声音可能被分到多个用户，而在识别之前混入了另一个声音的轨道会把该声音保存到被识别的用户。
* 短语音会延续到下一个片段，因此会话最后的几个短句可能保持未归属。从混合了未识别说话人与已验证用户的批次中提取的记忆归已验证用户所有，含两个已验证用户的批次归两人共同所有。
* 在新参与者被识别之前提交的环境记忆，保留在该参与者的临时身份下；达到会话的关闭超时时，会话最后的环境观测可能不会写入。
* 多个 Host 并发首次使用同一存储的情况，已在 LanceDB 和 Qdrant 的内存客户端上验证；没有在 Qdrant 服务器或复制集群上运行过，在那些环境中结果取决于集群的一致性设置。
* Doctor 只运行一个固定场景。它不覆盖设备、RTC 交付、摄像头寻址、并行 worker 或长时间运行。
* 已安装的基础运行时会在首次使用时重新编译部分标准库字节码，并将其写入已安装的基础目录。

### 未包含

* Web、移动或桌面 App，以及终端 UI。App 仍是计划中的工作。
* 默认与说话人的语音同时进行的流式转写、从第一个短句开始的合成，以及预先建立的 Provider 连接。这些是本版本之后的延迟优化工作。
* 持久的 Episode、持久的 Context、暂停／继续与恢复，以及会话重连。
* Memory 记录、声纹或向量索引的自动迁移或重建。
* 计划中的 `alphaavatar test` 能力测试命令。

### 说明

* 默认的人脸模型 InsightFace `buffalo_l` 仅授权用于非商业研究；商业使用需要获得 InsightFace 的许可。部署 Persona 人脸识别之前请先确认这一点。
* LiveKit 仍是已实现的 RTC 后端；通用后端契约不表示已有其他实现。
* 内部契约继续优先保证一致的演进，而不是向后兼容。

### 架构方向

v0.6.9 把原生运行时变成一个人可以自行安装、配置和检查的系统：

```text
install.sh ── base package (CPython 3.13, alphaavatar)
                 |
                 +-- config init / setup ── bundles and profiles, stored credentials
                 |                            |
                 |                            v
                 |                     plugin environment (plan, install, validate)
                 +-- doctor ── static checks ── runtime diagnosis (fixed samples, metrics)
                 +-- upgrade / cleanup ── forward switch, removal of unused builds
                 +-- start / dev
                        |
                        v
                   AvatarHost
                    +-- InferenceRuntime (shared runners, workers, metrics)
                    +-- execution: AvatarRuntime and AvatarEngine
                                     +-- ParticipantRuntime (participants of each Turn)
                                     +-- Router / Memory / Persona / Tools
```
