## 1. 结论

- **不建议本轮用 `multilingual-e5-small` 替换 Memory 被动检索的 embedding。** 用户已接受，继续使用 `text-embedding-3-small`。
  - 在当前检索管线和本组数据上，质量明显低于 `text-embedding-3-small`：174 条有相关记忆的查询中，Recall@5 为 0.647 对 0.879，配对差 −0.233，95% CI −0.299 ～ −0.170；测试集（查询划分，见下）上为 0.655 对 0.902。
  - 跨语言是最大的短板，Recall@5 只有 0.250（OpenAI 0.875）；中英混合 0.579，同义改写 0.575。
  - 中文查询配中文记忆时接近（0.897 对 0.926）。
  - 按 top-1 分数区分"有没有相关记忆"的能力弱。测试集 AUC 为 0.743 对 0.914，按连续分数计算，与阈值无关。各自在校准集选阈值后，测试集上有相关记忆的查询保留 0.460 对 0.897，无相关的被拒 0.833 对 0.722（第 5 节）。
- 它的优势是延迟和不依赖网络。被动检索环节（Runner 请求加 SQLite 解析，不含进程间转发）中位 20.7 ms、P95 75 ms（4 线程），OpenAI 为 210 ms、260 ms，中位约少 189 ms。
  - 这是检索环节的差，不等于端到端必然少同样的时间；被动检索和其他环节怎样重叠，本轮没有测。
  - 3 s 是被动检索的等待上限，不是忽略这段延迟的理由。本轮的判断是：这段延迟优势抵不过测到的质量差距。
  - 费用很低：本轮全部基线调用约 0.0012 美元。
- 设备端代价不小：fp32 模型 449 MB，加载后进程 RSS 比基线多约 0.78 GB，长输入时峰值约 1.08 GB。官方 int8 量化版为 113 MB、加载后多约 0.45 GB，但质量再降一点（Recall@5 0.615，跨语言 0.125）。OpenAI 没有本地模型权重，但冷进程创建客户端后也多约 0.63 GB，主要是库的导入，其中约 41 MB 是评测自己的 token 计数（第 6 节）。
- 适用范围：
  - 结论限于当前检索管线和本组合成数据。管线指第 2 节的生产 query 构建、检索文本、owner／scope 过滤和无阈值取前 10。数据是 380 条记忆、210 条查询，覆盖中文、英文、中英混合、同义改写、跨语言和无相关记忆（第 4 节）。
  - 测试集只是查询的划分：与校准集共享同一个记忆库和同样的合成用户，只说明阈值和指标在没参与选择的查询上是否稳定，不能直接外推到真实用户。
  - 只评测了 `multilingual-e5-small` 一个本地模型。结论是本轮不替换，不说明本地 embedding 路线不可行；其他模型、query 构建和检索方式都没有评估。
  - 性能结论只代表这台服务器 CPU（Xeon 6982P-C，16 vCPU），不推断手机性能。

## 2. 生产链路核对

按当前代码，评测走的就是这些步骤：

| 环节 | 生产代码 | 行为 |
|---|---|---|
| query 构建 | `PassiveRecall._remember`、`_schedule` | 每轮文本取末尾 `max_query_chars`（8192）后去空白；同一 context 保留最近 `search_context`（3）轮；拼成 `### user:\n<文本>` 块，用 `\n\n` 连接，整体再取末尾 8192 字符。当前轮在最后，字符截断优先保留当前轮 |
| 检索文本 | `serialize_memory_items`、`MemoryItem.embedding_text(include_topic=True)` | 记忆行：`topic` + 换行 + `value`（`[CONV]…[/CONV]`）；另外每个图节点（node_mentions 归一化后的节点）各一行，文本为节点 `content` |
| owner／scope 过滤 | `MemoryStore.recall_by_context`、`LanceDBRunner._where` | owner 为 Avatar 加当前已接受身份的用户；scope 为 `owner:*`、`episode:<当前>`、`context:<当前>`；LanceDB 的 where 先过滤，SQLite 的 `resolve_current` 按同样条件权威解析，最后 `visible_items` 再过滤一次 |
| 排序 | `_search_by_context`、`_merge_candidates` | 记忆行和图节点行各取 cosine 前 `recall_num × 3`（30）条，同一记忆取两者最高分，合并后取前 30；`resolve_current` 保持候选顺序，取前 10 交给模型；没有分数阈值 |
| 空库 | `_stored` | 这些 owner／scope 下没有记录时直接返回，不做 embedding |

harness 直接调用上面这些生产函数：用 `LanceDBRunner.run` 发出与生产相同的 `search_by_context` 请求，构建方式与 `tests/storage/test_lancedb_recall.py` 相同，只替换 `_embeddings`。只有两处没有覆盖：Runner 进程之间的 socket 转发，以及 `PassiveRecall` 等待 Turn 提交的那段。两个模型这部分的开销相同。

## 3. 模型与运行方式

- 来源：Hugging Face `intfloat/multilingual-e5-small`，MIT 许可，固定 revision `614241f622f53c4eeff9890bdc4f31cfecc418b3`。
- 使用的文件：官方仓库内的 `onnx/model.onnx`（fp32，sha256 `ca456c06…`）、`onnx/tokenizer.json`（与根目录的相同，sha256 `0b44a9d7…`）；int8 用同一仓库的 `onnx/model_qint8_avx512_vnni.onnx`（sha256 `dd476dd0…`）。
- 按模型卡的要求：
  - query 加 `query: `，记忆行和图节点加 `passage: `；
  - XLM-R tokenizer，最长 512 token，超出从右侧截断；
  - 按 attention mask 对 `last_hidden_state` 做平均池化，再 L2 归一化。
  - ONNX 只输出 `last_hidden_state`，池化和归一化在 numpy 里做。
- ONNX Runtime 1.23.1，CPUExecutionProvider。线程：`intra_op_num_threads` 按项目里 ONNX Runner 的规则取 `min(CPU 数 // 2, 4)`，这台机器上为 4；`inter_op_num_threads` 为 1。另外测了 1、2 线程。
- 与原模型的一致性：对照官方 PyTorch 写法（transformers 4.57.1、torch 2.9.0，用仓库里的 safetensors），覆盖本轮全部 1116 条文本（380 条记忆、526 个图节点、210 条生产 query，其中 21 条被截断）：

| 项目 | fp32 ONNX | int8 ONNX |
|---|---|---|
| token id 不一致 | 0 | 0 |
| 与 PyTorch 向量的余弦（最低／中位） | 0.99999984 / 1.0000000 | 0.98811 / 0.99684 |
| 向量分量最大差 | 1.4e-7 | 0.031 |
| 两两相似度最大差 | 1.2e-6 | 0.039 |
| 最近邻一致 | 99.7%（3 条不同，均为分差 ≤1.2e-6 的并列） | 81.3% |

## 4. 数据集与索引

- 数据集是合成的隔离数据，不读任何真实工作区或用户数据。
  - 格式按生产提取器的输出写：`[CONV]` 块、topic、node_mentions。
  - 由子代理按同一份说明编写，我做了全量校验和抽查：键唯一；标注都存在且对查询用户可见；`none` 没有标注；每个 value 恰好一个 `[CONV]` 块；共抽查 25 条查询，标注正确。
  - 局限：不是真实对话，标注可能有少量噪声。
- 记忆 380 条：
  - Avatar 20 条；用户 lin、emma、chen 各 100 条；每个用户另有一个干扰用户（zhou、mike、wang）各 20 条，逐条仿写该用户的记忆。
  - 语言：中文 147，英文 233。提取提示是英文，中文对话也可能写出英文记忆，所以 lin 约 40% 用英文，chen 一半一半。
  - scope：`owner` 335 条；`episode:E1` 15、`context:C1` 15 条，可见；`episode:E2` 9、`context:C2` 6 条，不可见，故意写成会被某些查询命中的内容。
  - 图节点 526 个。每条记忆尽量有相近但不同的困难负例。
- 查询 210 条：
  - 当前 episode `E1`、context `C1`，用户身份已接受。
  - 每条 1～3 轮，按生产方式构建：1 轮 79、2 轮 109、3 轮 22。
  - 类别：中文 34、英文 38、中英混合 38、同义改写 40、跨语言 24、无相关记忆 36。无相关记忆中有 13 条问的是只有干扰用户或不可见 scope 才有的内容。
  - 按 id 哈希在每个类别内交替分成校准集和测试集，各 105 条。这是查询的划分：两组共享同一个记忆库和同样的合成用户，测试集只说明阈值和指标在没参与选择的查询上是否稳定，不等于独立的真实用户数据。
- query 长度（生产格式）：

| 项目 | 中位 | P95 | 最大 |
|---|---|---|---|
| 字符 | 93 | 1752 | 3753 |
| e5 token（含前缀和特殊符号） | 42 | 865 | 948 |
| OpenAI token（cl100k） | 46 | 1229 | 1432 |

  - e5 token 分布：<32 有 53 条，32～127 有 94 条，128～511 有 42 条，≥512 有 21 条。
  - 生产 query 拼接最近三轮后保留末尾 8192 字符，本身优先保留当前轮。本轮最长 3753 字符，这一步没有截掉内容。
  - 当前轮被截掉发生在后一步：e5 tokenizer 按模型卡在 512 token 处从右侧截断。超过 512 的 21 条（10%）都是 3 轮的查询，当前轮在末尾，全部被截掉。OpenAI 一侧最长 1432 token，没有截断。
  - 记忆行和图节点最长 86 token，没有截断。
- 索引：
  - 两个模型用同一份 SQLite 记录（真实的 `SQLiteMemoryStore` 逐条提交），各自用 `LanceDBRunner._save` 重新生成向量，写入各自独立的 LanceDB 目录：`runs/<模型>/index`，1536 维与 384 维，各 906 行。
  - 按 outbox 的默认批量 64 条提交。不同模型的向量没有混用。
  - 磁盘占用：OpenAI 索引 6.4 MB，e5 索引 2.5 MB，记录 2.0 MB。

- 配对 bootstrap（4000 次，对 OpenAI）：
  - e5 fp32：Recall@5 −0.233（95% CI −0.299 ～ −0.170），nDCG@10 −0.256（−0.303 ～ −0.210），测试集 Recall@5 −0.247（−0.339 ～ −0.161）。
  - int8：Recall@5 −0.264（−0.339 ～ −0.190）。
- 「保留末尾」是诊断变体，不是模型卡的用法：超过 512 时保留 `<s> query:` 和最后 510 个左右的 token，让当前轮留在输入里。被截断的查询只从 0.056 升到 0.111，整体几乎不变。截断不是主要原因。
- 阈值：生产不设分数阈值，固定交前 10 条。这里比较的是"按 top-1 分数判断有没有相关记忆"的能力。
  - AUC 按 top-1 的连续分数计算，即有相关记忆的查询分数高于无相关查询的概率，与选哪个阈值无关。
  - 保留率、拒绝率和加阈值后的 Recall@5 才取决于阈值：各模型在校准集上按平衡准确率选阈值，再用到测试集。e5 的分数挤在 0.85～0.89，不能沿用 OpenAI 的阈值。

- owner／scope 过滤：
  - 换 embedding 后仍然生效。四个模型变体下，210 条查询的最终结果和 Runner 返回的候选里，不可见记忆都是 0 条。

## 6. 延迟与资源

- 独占运行，期间机器负载约 1～2。
- 每个 e5 配置：1 个完整进程（预热后 210 条生产 query 各跑两遍，生产检索链路两遍），另加 4 个只测加载的新进程。
- OpenAI 的加载和首次请求测了 3 个新进程。预热后的请求直接用质量那一遍的 210 次真实调用，不重复付费。
- 时间单位为 ms，格式为"中位 / P95（样本数）"。

- 空库对照：两个模型的 210 条查询都走 `empty` 分支（Runner 在 embedding 之前返回），没有返回记录，整体约 2.1 / 2.5 ms；e5 的 embedding 调用计数前后不变。所以空库的结果不能代表模型延迟，上表来自有合格候选的数据集。
- 内存：进程 RSS，单位 MB，格式为"中位（进程数）"。

## 8. 后续观察，未改

- 长 query：
  - 生产 query 拼接最近三轮后保留末尾 8192 字符，本身优先保留当前轮。当前轮被截掉，发生在 e5 tokenizer 的 512 token 右侧截断这一步（第 4 节）。
  - OpenAI 在 ≥128 token 的查询上 Recall@5 为 0.735，<32 token 的为 0.952；e5 会截断的那 18 条为 0.389，OpenAI 一侧并没有截断它们。但长短两组是不同的查询：长组 51 条中有 18 条只有 1 轮、当前轮本身就长，当前轮中位 71 字符；短组 42 条都是 1 轮，当前轮中位 30 字符。内容和难度也不同，OpenAI 也没有做只用当前轮的对照，不能据此认定历史拼接导致召回下降。
  - 记为后续观察，query 策略不改。
- 如果以后要接入本地 embedding，几处需要一起处理：
  - 文本前缀：被动检索用 query／passage；整合候选检索 `search_similar_batch` 是对称相似度，模型卡建议两侧都用 `query: `。
  - 维度从 1536 变成 384 后，`_validate_collection_schema` 只检查列不检查维度，已有索引必须新建集合并重建。
  - 设备端的内存占用。
  这些都不在本轮范围。
