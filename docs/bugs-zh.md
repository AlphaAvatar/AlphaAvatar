# AlphaAvatar 缺陷记录

这里记录当前已知缺陷和已修复项。复现细节和历史验证见 [2A 开发日志](agent-logs/2026-10/2026-10-25/claude-code-2a-zh.md)、[Doctor 开发日志](agent-logs/2026-11/2026-11-03/claude-code-doctor-zh.md)、[Context 开发日志](agent-logs/2026-11/2026-11-04/claude-code-context-zh.md)及 [Speaker Vector 日志](agent-logs/2026-11/2026-11-10/claude-code-speaker-vector-zh.md)。设计限制和延期的产品决策与已确认缺陷分开记录。

## 已知缺陷

| 编号 | 问题 | 当前状态 |
| --- | --- | --- |
| KD-19 | 固定的两句样本经分段 STT（`gpt-4o-transcribe`）转写时，经常只剩第一句。 | 遗漏发生在 STT 服务返回的文字里，插件如实传递；改停顿、换声线无效，指令式第二句最容易整句丢失（第五批）。第六批用当前可用、插件支持的模型对照（同一批样本、自动语言、不加提示）：`gpt-4o-transcribe` 两句都在 7/20，`gpt-4o-mini-transcribe`、`gpt-transcribe`、`whisper-1` 都是 20/20；但在独立多句、中英混合和同会话切换语言的 27 段里，默认 27/27，`gpt-transcribe` 24/27（英文句中的中文词改写成拼音），mini 21/27（中文词译成英文或拼音、一次地名错、切换后输出繁体）；`whisper-1` 慢约一倍。没有候选全部通过，默认仍为 `gpt-4o-transcribe`、自动语言、不加提示（Doctor 日志第六批）。按已知模型限制保留：诊断日志第 10 节的 VAD 对照中，两个阈值下都有单段内缺句。系统验收看音频完整提交、跨段累计、终态与取消、超期结果隔离和诊断是否准确，不以固定样本全部答对为准，不再为此扩大模型实验（诊断日志第 11 节）。 |
| KD-41 | persona（说话人）：参与者改绑到另一个用户时，只清空载入的资料和运行状态，本次会话已攒的声纹向量不清空，人脸向量和对话里提取的资料也一样，改绑前的这些会一并保存到新用户。认错后纠正时这样是对的（例：alice 第一段被误认成 bob，之后认出 alice，会话声纹全是 alice 的）；跟踪先混进了另一个人的声音再改绑时，别人的声音会写进新用户（例：bob 说 6 秒后 alice 被并进同一条跟踪、说 9 秒并认出，会话声纹约 40% 是 bob 的，每次保存带入约 2%）。 | 根本原因是匹配问题（跟踪误加入、检索误认），不是改绑或保存的逻辑；延期，随跟踪与检索的匹配优化处理（Speaker Vector 日志第五批、第十批之后的决定）。 |
| KD-47 | persona（说话人）：`_consume_loop` 在整批观测处理完之后才确认。一条观测处理时持续抛出，这一批每 50 毫秒从上次确认的位置重读一次，说话人消费者停住，所有来源的说话人处理都停下，直到这条记录被挤出流的保留范围，再以缺口放弃其间所有的段（KD-53 之后，已确认的关联保留，未完成的段作废）。会持续抛出的路径：`observe_source` 的来源达到上限 256（正常使用中碰不到）。原来建 state 时 `ensure_entity` 失败的路径，已随说话人不再接受上游给的实体而删除（人脸日志第五批）。 | 用户决定登记，留待后续 review（Speaker Vector 日志「精简说话人处理器」）。 |

## 已修复

按代码所在的位置分节：插件分 foundation、perception、tools 三类；插件之外，Host、运行时与核心库、工具脚本与测试基础设施各一节。插件的配置模型在 `avatar-agents/alphaavatar/agents/configs/plugins/` 等处，按它所属的插件类别归入。

### 插件 · foundation（context、loop、provider、voice）

| 编号 | 问题 | 修复 |
| --- | --- | --- |
| O-10 | voice：启用 STT 插件而没有 `voice.stt.model` 时，`config check` 和 Doctor 的配置检查都能通过，到 start 装配会话时才报错；`voice.tts.model` 则在配置校验时就检查。 | 检查移到 `STTConfig` 的字段校验：启用 STT 插件时，model 缺失、为空串或全空白都拒绝，关闭时不需要。config check、Doctor、setup、start 都经同一次配置校验，诊断定位到 `voice.stt.model`；装配会话时的检查随之去掉（诊断日志第 13 节）。 |
| KD-7 | loop：工具默认审批行为与部分示例文档不一致。 | 默认 `approval_required: false` 是既定行为（用户 2026-11-18 确认），只改文档：`tool_policies: {}` 下已授予 Run 的能力不再二次审批；`enabled: false` 拒绝，`approval_required: true` 需要授权方，原生 Host 不提供，这样的能力不提供给模型。README 和示例 YAML 注释已与此一致（[README 日志](agent-logs/2026-11/2026-11-18/claude-code-readme-zh.md)）。 |
| KD-46 | context、loop：Context 没就绪时抛出 `TimeoutError("Required Turn context is not ready")`，被 Loop 当成自己的预算超时：探索阶段记为 `time_budget`，不再调用工具，直接进入只回答的收尾；收尾时仍不就绪则以 `failed / timeout` 结束，不请求模型。 | 按用户的决定，Context 不再抛出，记一条 warning（带 `turn_id` 和仍在等的消费者）后照常准备：它等的都是可以没有的证据。Turn 已不是它输入当前的快照时，Memory、Persona 的 `content_for` 仍以 `ValueError` 拒绝，Run 以 `execution_failed` 结束。回归 `test_a_turn_whose_context_is_not_ready_is_still_prepared_and_says_so`，改回抛出、去掉 warning 时都失败；Loop 探测中只有第一次失败、每次都失败两种情况，Run 都以 `completed` 结束，带工具请求一次模型（Speaker Vector 日志第十一批之后）。 |
| KD-18 | context：每轮请求都重发 History 中的全部图片，累计内联字节超过 Responses `max_inline_bytes` 后，此后每一轮都被拒，纯文字轮也一样。 | History 仍完整保存。请求把历史图片（用户消息和工具输出）在原位置换成 `<image_not_replayed />`，只有本轮图片内联发送。 |
| KD-22 | provider：OpenAI Responses 的 `model.request_sent` 在 `create()` 返回或抛错后才记，晚于请求真正交给传输层，Doctor 据此算的发送时刻偏晚。 | 发送时刻改由 httpx 请求钩子在交给传输层时逐次记录，每次尝试一条。 |
| KD-27 | voice：分段 STT 请求计时（`stt.request`）的首事件和终稿两项，起点取成请求头写完，而不是收到应答头，多算了上传和服务等待。 | 两项改从 `receive_response_headers.complete` 起算，真实基线里首事件为 0.4～3.0 ms。 |
| KD-28 | voice：没有 trace 的 STT 请求（调用方自带 `client=`，或在交给传输层之前就失败）被记成 `reused=True`。 | 只有 trace 看到请求头发出且没有建连才记复用，未观测时不记；Doctor 对这类请求只给排队一行，其余写 "not observed"。只有离线验证。 |
| KD-30 | voice：每个进程第一段 STT 请求要在事件循环上做 openai SDK 的懒加载（首次访问 `client.audio.transcriptions`），约 95～103 ms 落在首段的请求路径上。 | STT stream 打开时在线程里预先访问，请求等它完成，不在事件循环上导入。真实运行里，首段没有落在任何网络段的时间从约 98 ms 降到约 3～6 ms，本次未观察到输入延迟增加；约 97 ms 的首次加载已移出请求关键路径，端到端收益仍待验证。 |
| KD-20 | 同一 STT stream 连续多段时，每段都新建 TCP 和 TLS 连接。 | 读原始响应，过了 `[DONE]` 仍读到 body 结束，读取与关闭共用期限。真实服务上同一 stream 连续 5 段，后 4 段都复用连接（2 次共 8/8），收尾 0.3～3.9 ms（Doctor 日志第四批）。 |
| KD-32 | SSE 只按 LF 分行，CR 换行的事件被拼成错误的 JSON；第一次修复把块末尾的 CR 暂存，以 `\r\r` 结束的完整终稿要等下一块数据才发布，收尾期限也不启动。 | 用 `iter_text()` 解码字符，按 CR、LF、CRLF 分行；不用会在 `\u2028` 处断行的 `iter_lines()`。CR 立即结束一行，跨块 CRLF 的 LF 跳过（第五批）。 |
| KD-33 | 无效终稿（`text: null`）在请求日志里被记成成功的 final。 | 有效终稿发出后才记录；日志的 outcome 与消费者收到的终态一致。 |
| O-15 | provider：每个 runtime 的第一个模型请求，在 Context built 之后多约 90～160 ms：client 构建，以及 SDK 在事件循环上首次加载 `client.responses`。 | Loop 初始化时在线程里构建 client 并加载 Responses 资源，请求等同一个任务。同一 WAV 的真实对照里，第 1 轮 Context built → Model request sent 从 122 ms 降到 6.7 ms（视觉开从 151 降到 8.2）。第 1 轮首音频没有下降（4,137 对 4,276 ms），仍比后续轮慢约 0.7 s，主要是模型首事件多约 450 ms、终稿到提交多约 130 ms（Doctor 日志第五批）。 |
| O-17 | loop：Engine 关闭时打断一个刚答完、正在回收身份监视任务的 run，取消落在 `finally` 的这一步，run 没有给出结果而是自己以取消结束；它的 watcher 随之失败，Engine 关闭报错，Doctor 的 Ctrl+C 用例 `session.cleanup` 判 FAIL（进程组和资源都已回收）。第六批 20 次中复现 3 次。 | 回收身份监视任务时的取消与其他收尾步骤一样处理：监视任务照常结束，run 仍归结为 CANCELLED 结果。确定性用例复现修复前的失败；修复后两个 Ctrl+C 用例 40/40 通过，变异被抓到（第六批）。 |
